Este documento explica la implementación del esqueleto FastAPI que convierte al prebenchmark —hasta ahora una herramienta de consola— en una aplicación con interfaz web. El foco está en una decisión concreta: las corridas de entrenamiento se ejecutan en un hilo aparte, de modo que el proceso HTTP y el componente principal de la página sigan respondiendo mientras PyTorch entrena. Además se detalla qué hace cada módulo de server/ y cómo cada uno se apoya en la estructura que ya existía, sin duplicar el dominio.

1. Qué se construyó y por qué

El paquete prebenchmark/ ya resolvía el problema científico: registrar configuraciones, entrenarlas de forma reproducible, compararlas contra una línea base, agregar repeticiones por semilla, exportar tablas y generar un informe estadístico. Su interfaz era la línea de comandos. Eso es correcto para un barrido de 36 configuraciones × 5 semillas, pero es incómodo para el trabajo exploratorio: probar una combinación, ver la curva de pérdida en vivo, cancelar si va mal, y comparar dos o tres corridas sin escribir un comando distinto cada vez.

La aplicación nueva no reemplaza al prebenchmark: lo expone. Se agregó una capa server/ que traduce HTTP ↔ dominio. El benchmark definitivo, entonces, no es un segundo sistema con su propia lógica de entrenamiento; es una fachada sobre el mismo núcleo, para que la evidencia que produce la UI sea comparable con la que producen las suites.

La idea en una frase. El navegador pide una corrida, recibe un job_id al instante, y se suscribe a un flujo de eventos; el entrenamiento ocurre en un hilo del servidor que no bloquea ni al event loop de FastAPI ni a la página, y el resultado queda persistido en el mismo formato que usa el resto del proyecto.

2. El problema central: entrenar sin congelar la página

Entrenar un MLP no es una operación de red: es cómputo intensivo y sostenido. Una corrida puede durar desde unos segundos hasta más de un minuto (el tope de 500 épocas en satimage se midió en torno a 122 s). Si ese trabajo se ejecuta en el mismo hilo que atiende las peticiones HTTP, el servidor deja de responder: no se puede consultar el estado, no se puede cancelar y la página parece colgada.

2.1 Por qué el entrenamiento no puede ser una corrutina más

La tentación natural es escribir el endpoint como async def y hacer await del entrenamiento. Eso no funciona y conviene entender por qué:

  • El entrenamiento es código síncrono y bloqueante. runner.run_experiment es una función común: recorre épocas y batches con PyTorch. No hay puntos de await reales dentro de ese bucle. Si la llamás desde una corrutina, bloqueás el event loop hasta que termina.
  • Un await no vuelve mágicamente concurrente a una función síncrona. Para ceder el control habría que reescribir el runner con asyncio, y ni PyTorch ni el resto del paquete están diseñados así. Sería una reescritura invasiva del núcleo, justo lo que se quería evitar.
  • El event loop es un recurso compartido. Mientras está ocupado entrenando, no puede aceptar conexiones, servir /api/health, ni mantener abierta la conexión SSE que transmite las épocas. Todo el servidor queda de rehén de una sola corrida.

La conclusión es la correcta para este tipo de carga: el trabajo pesado va a un hilo, y el event loop queda libre para la coordinación. PyTorch libera el GIL durante las operaciones numéricas, así que el hilo de entrenamiento realmente aprovecha la CPU; y aunque no lo hiciera, el objetivo principal —que el servidor siga atendiendo— se cumple igual porque el bloqueo está acotado al hilo de trabajo.

2.2 La solución: un hilo de trabajo y un estado observable

El patrón implementado es submit → observar. El endpoint POST /api/runs no entrena: valida, crea un objeto Job, lo encola en un ThreadPoolExecutor de un solo hilo y responde 202 Accepted con el identificador. El entrenamiento corre en ese hilo; la página se suscribe a GET /api/runs/{id}/events y recibe eventos a medida que se producen.

NAVEGADOR SERVIDOR (proceso único) ───────── ────────────────────────────────────────────────────── ┌─ Event loop (asyncio) ─────────────────────────┐ POST /api/runs ──────────────────►│ valida → crea Job → registry.submit(job) │ ◄──── 202 { job_id } ─────────────│ responde YA, sin entrenar │ └──────────────────────┬─────────────────────────┘ │ executor.submit ┌──────────────────────▼─────────────────────────┐ GET /api/runs/{id}/events ───────►│ Hilo "prebenchmark-ui" (1 worker) │ (SSE, conexión abierta) │ runner.run_experiment(...) │ ◄──── event: epoch ───────────────│ on_epoch → job.publish_epoch(record) │ ◄──── event: epoch ───────────────│ should_stop ← job._cancel │ ◄──── event: done ────────────────│ mark_done(resultado) │ └────────────────────────────────────────────────┘

El puente entre ambos mundos es el Job. No es un objeto pasivo: es el estado compartido y observable de una corrida. El hilo de entrenamiento escribe en él (agrega eventos, marca estados); el event loop lo lee (para el SSE, para el snapshot de estado, para cancelar). La sincronización se resuelve con un threading.Lock para la lista de eventos y un threading.Event para la cancelación. No hay memoria compartida sin protección entre los dos hilos.

2.3 Quién hace qué: los cuatro ejecutores del sistema

Es fácil confundir "asíncrono" con "en otro hilo". En esta implementación conviven cuatro contextos de ejecución distintos, y cada uno tiene una responsabilidad acotada:

ContextoQué ejecutaPor qué ahí
Event loop (asyncio) El endpoint SSE run_events y la generación de eventos. Necesita esperar sin bloquear: await asyncio.sleep(0.05) entre lecturas. Debe quedar libre para atender otras conexiones.
Threadpool de Starlette Los endpoints declarados con def (no async def): health, options, validate, create_run, etc. FastAPI los ejecuta en un pool de hilos precisamente para no bloquear el loop. Las operaciones son cortas (validar, leer metadatos).
Hilo de entrenamiento (ThreadPoolExecutor, max_workers=1) Service._execute → runner.run_experiment. Es el trabajo largo. Un solo hilo garantiza que nadie más pise los RNG globales (ver §4).
Navegador app.js: fetch, EventSource, dibujo de la curva. Consume el estado. No entrena ni calcula métricas: solo presenta lo que el servidor emite.
Resultado práctico. Mientras una corrida entrena, la página puede seguir cambiando de pestaña, consultar el estado, ver evidencia de las suites o pedir la cancelación. El servidor nunca deja de responder porque el cómputo vive fuera del event loop.

3. El ciclo de vida completo de una corrida

Los pasos, en orden, con las funciones reales que intervienen:

1. El cliente envía la configuración. POST /api/runs con un JSON que cumple RunRequest. Pydantic valida forma: tipos, lr > 0, max_epochs entre 1 y 5000, device dentro del conjunto permitido.
2. Se construye la configuración de dominio. _build_config parte de pb_data.dataset_base_config(dataset) —que deriva input_dim y output_dim de los datos reales— y aplica los parámetros libres con dataclasses.replace. El early stopping se traduce a ConvergenceSpec(enabled=request.early_stop).
3. Se valida con las reglas del dominio. space.validate_config(cfg) devuelve VALID, WARNING o INVALID. Si no es ejecutable, el endpoint responde 422 con el detalle de la validación y no se encola nada.
4. Se crea y encola el job. Job(dataset, config, include_test, validation) nace en estado queued. service.registry.submit(job) lo registra en memoria y lo entrega al executor. El endpoint responde 202 con job_id y la validación: el cliente ya puede abrir el flujo de eventos.
5. El worker arranca. Service._execute llama job.mark_running() (estado running, evento status) y ejecuta runner.run_experiment(cfg, experiment_id, store, on_epoch=job.publish_epoch, should_stop=job.should_stop).
6. Cada época se publica. El runner invoca on_epoch(record) con la misma forma que una fila de epochs.csv. Job.publish_epoch la convierte a JSON estricto y la agrega al log de eventos bajo el lock.
7. El SSE la entrega. El generador de run_events lee events_from(index) cada 50 ms, emite lo nuevo con event: epoch y avanza el índice. Si no hay novedades durante 15 s, envía un comentario : ping para mantener viva la conexión.
8. La corrida termina de tres formas posibles. mark_done(resultado) si el runner devolvió un resultado (incluido INCOMPLETE por cancelación); mark_failed(mensaje) si lanzó una excepción. En ambos casos se agrega el evento terminal y se cierra el flujo.
9. El resultado se materializa. _result_payload arma la respuesta: expone validation_metrics, el execution_state, la configuración aplicada, space_key y group_key. final_metrics (test) se elimina salvo que el request tenga include_test=true. El store conserva el dato completo.

La corrida es la fuente de verdad; el observador es prescindible. Si on_epoch fallara, el runner lo ignora y el entrenamiento continúa. Ese contrato está documentado explícitamente en runner.run_experiment y es lo que permite que la UI sea un consumidor y no un socio del entrenamiento.

4. El contrato de concurrencia: exactamente un worker

JobRegistry lanza ValueError si se lo instancia con max_workers != 1. No es una limitación pendiente: es una decisión de reproducibilidad. El motivo está en el runner: 

# prebenchmark/runner.py — inicio de cada corrida
seed = cfg.seed if cfg.seed is not None else 42
np.random.seed(seed)
torch.manual_seed(seed)
if torch.cuda.is_available():
    torch.cuda.manual_seed_all(seed)

Esos sembrados son globales al proceso. De ellos dependen la partición train/val/test y la inicialización de pesos. Si dos entrenamientos corrieran a la vez en el mismo proceso, cada uno pisaría el estado global del otro y los resultados dejarían de ser reproducibles. Un solo worker garantiza que cada corrida vea exactamente el RNG que sembró, desde la primera hasta la última época.

Consecuencia operativa. Las corridas se encolan: si llegan tres pedidos, se ejecutan una tras otra. El estado queued existe justamente para eso, y el frontend muestra "Esperando al worker…" cuando todavía no arrancó. Para paralelizar barridos independientes hay que usar procesos, no hilos: cada proceso tiene su propio estado global de RNG. Eso queda fuera del esqueleto actual y se discute en §11.

El executor se crea con thread_name_prefix="prebenchmark-ui", lo que hace que los hilos se vean identificables en un profiler o en un traceback. Al apagar la aplicación, el lifespan llama registry.shutdown() con wait=False, cancel_futures=True: no se cuelga esperando una corrida larga, pero tampoco deja tareas nuevas encoladas.

5.1 app.py — composición, rutas y adaptación fachada

Qué hace. Es el composition root. Define create_app() como fábrica (no un módulo con estado global), monta los estáticos, declara todos los endpoints y construye el Service de larga vida dentro del lifespan.

Qué aporta. Concentra la traducción entre HTTP y dominio. Tres funciones son el corazón de esa traducción:

  • _build_config(request) — convierte un RunRequest en un ExperimentConfig real, usando la configuración base del dataset y replace.
  • _result_payload(result, job) — convierte el resultado del runner en la respuesta de la API, aplicando la política del set de prueba y calculando las claves de identidad.
  • _dataset_payload(name, force_load) — describe un dataset sin descargarlo por sorpresa: el listado solo reporta lo cacheado; el detalle sí resuelve y cachea.

El Service. Guarda lo que debe sobrevivir a cada request: el ResultsStore aislado, el experiment_id, las raíces de export/report y el JobRegistry. Se crea una vez al arrancar y se cierra al apagar. Su método _execute es el único lugar donde se llama al runner.

Por qué una fábrica. create_app acepta store_root, experiment_id, exports_root y reports_root. Eso permite montar la app en tests con un store temporal, sin tocar results/ ni depender de variables de entorno. El módulo termina con app = create_app(), que es lo que consume Uvicorn.

Detalle de arranque. _configure_torch_threads() respeta PREBENCHMARK_TORCH_THREADS si está definida. Con un solo worker, el valor por defecto de PyTorch (todos los núcleos) es el correcto; la variable existe para evitar oversubscription cuando el proceso convive con otras cargas.

5.2 jobs.py — el job, su máquina de estados y el pool de un hilo concurrencia

Qué hace. Define Job (estado observable de una corrida) y JobRegistry (registro en memoria + executor de un worker). Es el módulo que hace posible el patrón submit → observar.

El estado del Job. Campos públicos: dataset, config, include_test, validation, id, status, marcas de tiempo, execution_state, error, result, epochs_seen y cancel_requested. Campos privados: _events (log append-only), _done, _lock y _cancel.

La máquina de estados

queued ──mark_running()──► running ──mark_done()──► completed │ └──mark_failed()──► failed cancel_requested no es un estado del job: es una señal que el runner consulta al inicio de cada época. La corrida cancelada termina como completed con execution_state = INCOMPLETE.

Es importante no confundir status (estado del job en la cola) con execution_state (estado técnico de la corrida, el vocabulario del store: COMPLETED, COMPLETED_WITH_WARNINGS, FAILED, INCOMPLETE). Una cancelación no es un fallo del job: el job termina normalmente y el resultado dice INCOMPLETE. Esa distinción es la que permite excluir la corrida de los agregados sin perder la evidencia de lo que sí alcanzó a entrenar.

El log de eventos y la recolocación

_events es una lista append-only protegida por _lock. Se guarda completa (hasta MAX_RETAINED_EVENTS = 2000) en lugar de consumirse, para que un cliente que se reconecta pueda reproducir desde el principio en vez de perder las épocas ya emitidas. events_from(index) devuelve una copia de lo que hay desde ese índice más el flag _done; el SSE avanza su propio índice. Es un patrón de lector con cursor sobre un log inmutable: simple, sin condiciones de carrera y sin necesidad de una cola entre hilos.

Detalle honesto: al llegar a MAX_RETAINED_EVENTS se dejan de registrar épocas nuevas, pero epochs_seen sigue incrementándose y el evento terminal se agrega igual. Para el uso previsto (corridas de hasta 500 épocas por defecto) el tope no se alcanza.

La cancelación cooperativa

request_cancel() activa un threading.Event. El runner lo consulta al comienzo de cada época mediante should_stop. Por eso la cancelación no es instantánea: la época en curso termina antes de cortar. Es el compromiso correcto — abortar un paso de entrenamiento a la mitad dejaría el modelo y las métricas en un estado inconsistente.

El registro y la retención

JobRegistry guarda los jobs en un diccionario y mantiene un deque con el orden de llegada. Conserva los últimos MAX_RETAINED_JOBS = 50; al superar ese número, descarta el más viejo. recent(limit) devuelve los últimos en orden inverso (el más nuevo primero). Todo el acceso al diccionario y al deque pasa por un lock propio, distinto del lock de cada job.

Por qué en memoria. El esqueleto no necesita una cola persistente: el objetivo es la corrida interactiva, no la tolerancia a reinicios. El costo es explícito y está documentado en §10: si el proceso se reinicia, los jobs en vuelo se pierden (aunque lo ya persistido en el store sobrevive).

5.3 schemas.py — el contrato de la API borde

Qué hace. Define los modelos Pydantic de entrada y salida: RunRequest, ValidationOut, JobCreated y JobStatus.

Qué aporta. Valida forma, no metodología. Los valores permitidos y las reglas del experimento viven en prebenchmark.space y se aplican con validate_config. Esta separación evita el error clásico de tener dos fuentes de verdad que se desincronizan: si mañana se agrega una activación, se agrega en el dominio y la API la acepta sin tocar el esquema.

Decisiones codificadas en los defaults.

  • early_stop=True: las suites se corrieron con el criterio habilitado y sin él una corrida puede consumir las 500 épocas completas.
  • include_test=False: el set de prueba queda reservado. Solo se devuelve si el cliente lo pide explícitamente, y la respuesta lo marca como tal (test_hidden).
  • max_epochs acotado a [1, 5000] y lr > 0: los límites baratos se validan en el borde para no llegar al dominio con valores absurdos.

ClassWeight y Device son Literal: el conjunto cerrado se declara una vez y Pydantic lo rechaza antes de ejecutar nada.

5.4 serialize.py — JSON estricto para NumPy y NaN utilidad

Qué hace. to_jsonable(value) recorre recursivamente una estructura y devuelve solo tipos JSON estrictos.

Por qué es necesario. Los metadatos del runner incluyen objetos de NumPy (np.float64, arrays), Path y posiblemente NaN o Infinity. json.dumps no acepta esos tipos, y el JSON estricto tampoco acepta los no finitos. La función resuelve los tres casos:

  • float no finito → null (un NaN no es un número válido en JSON; convertirlo a null es preferible a emitir un documento inválido).
  • Path → str.
  • Objetos con tolist() o item() → se convierten y se vuelven a recorrer; si falla, se usa str(value) como último recurso.

Dónde se usa. En Job.publish_epoch (cada época), en _result_payload (respuesta final) y en el snapshot del job. Es la frontera que garantiza que lo que sale por HTTP siempre sea parseable por el navegador.

5.5 evidence.py — leer la evidencia de las suites solo lectura

Qué hace. Lee results/exports/<experiment>/master_*.csv (y aggregates_*.csv, configs_*.csv) y produce un registro por experimento con estadísticas por familia optimizer + lr. También localiza el informe HTML/PDF más reciente en results/reports/.

Qué aporta a la UI. Alimenta la pestaña de comparación y los avisos de "familia problemática" de la pestaña de corrida. La UI no tiene listas fijas de qué configuraciones son malas: las deduce de las corridas reales del dataset seleccionado.

Dos decisiones de diseño notables.

  • Ranking relativo, no umbral absoluto. Un F1 de 0.35 es pésimo en satimage (máximo ~0.898) y esperable en wine_quality (máximo ~0.346). Marcar "familias del fondo" del propio ranking evita comparar peras con manzanas.
  • El modo de fallo se infiere de las épocas ejecutadas. Una familia con F1 bajo y epochs_mean menor o igual a 0.5× la mediana del dataset colapsó temprano; una con F1 bajo y épocas mayores o iguales a 2× la mediana no convergió. Son causas opuestas (lr demasiado alta vs. demasiado baja) y la UI las explica distinto. El umbral relativo hace que "lento" signifique lo mismo en datasets con escalas de épocas distintas.

Seguridad. report_file rechaza experiment_id con .., / o \, y los informes se sirven por API con FileResponse. No se expone el sistema de archivos.

La lectura es bajo demanda en cada request: no hay caché. Es aceptable para la escala del esqueleto; si el número de experimentos creciera, el siguiente paso sería cachear por mtime.

5.6 static/ — el frontend sin build step cliente

Qué hace. index.html define la estructura de pestañas; styles.css los estilos; app.js la lógica del cliente. No hay bundler, transpilador ni node_modules: se sirve tal cual desde StaticFiles.

Qué aporta. Dos pestañas implementadas:

  • 1 · Corrida individual. Formulario de configuración, validación en vivo contra /api/validate, estimación de costo y avisos de la familia elegida, botón de correr, curva de pérdida en vivo por SSE, métricas de validación, matriz de confusión, visor de metadata.json, y comparación de hasta tres corridas con remoción por fila.
  • 2 · Comparación general. Lee /api/evidence y ofrece enlaces a los informes HTML/PDF generados por analyze.
  • 3 · Funciones de activación. Presente pero deshabilitada con la etiqueta "planificado". No se declara como implementada.

Cómo consume el servidor. api(path, options) centraliza fetch y el manejo de errores; openStream(jobId) abre un EventSource y registra listeners para status, epoch, done y failed; drawCurve dibuja la curva en canvas sin librerías. El estado del formulario vive en un objeto state y se envía como buildPayload().

El tercer botón existe en el HTML con disabled y title="Planificado para una etapa posterior". Es una decisión de producto: mostrar el rumbo sin fingir que está hecho.

5.7 __init__.py — la superficie pública paquete

Qué hace. Declara el paquete y expone create_app en __all__. Es deliberadamente mínimo: el punto de entrada para tests e integraciones es la fábrica, no los módulos internos.

6. Cómo se reutiliza la estructura original de prebenchmark

6.1 La regla: la UI no reimplementa el dominio

La decisión arquitectónica más importante del servidor es qué no hace. No carga datasets por su cuenta, no arma modelos, no entrena, no calcula métricas, no valida reglas metodológicas ni escribe resultados. Todo eso ya existe en prebenchmark/ y está probado. El servidor es una capa de adaptación: recibe HTTP, llama al núcleo, traduce la salida.

Prueba de la regla. El único lugar de server/ que ejecuta entrenamiento es Service._execute, y lo hace con una sola llamada: runner.run_experiment(job.config, experiment_id=..., store=self.store, on_epoch=..., should_stop=...). No hay un segundo bucle de épocas en el servidor. Si mañana cambia la métrica o el criterio de corte, cambia en el núcleo y la UI lo hereda.

6.2 Mapa de reutilización, módulo por módulo

Opciones válidas para el formulario config.KNOWN_ACTIVATIONS, KNOWN_OPTIMIZERS, KNOWN_INITIALIZATIONS, space.ParameterSpace.learning_rates /api/options las publica. El frontend no hardcodea el catálogo.

6.3 Los dos hooks nuevos del runner: on_epoch y should_stop

Para que la UI pudiera observar y cancelar sin duplicar el entrenamiento, el runner incorporó dos parámetros opcionales. Son la única extensión que el servidor necesitó del núcleo, y están diseñados para no cambiar el comportamiento cuando no se usan: 

def run_experiment(
    cfg: ExperimentConfig,
    experiment_id: str = "exp-test",
    store: ResultsStore | None = None,
    *,
    df: Any = None,
    on_epoch: Callable[[dict[str, Any]], None] | None = None,
    should_stop: Callable[[], bool] | None = None,
) -> dict[str, Any]:
  • on_epoch(record) — observador que recibe cada registro de época en el momento en que se produce, con la misma forma que una fila de epochs.csv. Un fallo del observador nunca aborta el entrenamiento: la corrida es la fuente de verdad, el observador es prescindible. La UI lo implementa con job.publish_epoch.
  • should_stop() — se consulta al comienzo de cada época. Si devuelve True, el bucle se corta y la corrida se registra como INCOMPLETE, un estado técnico que el análisis ya excluye de las métricas. La UI lo implementa con job.should_stop, respaldado por un threading.Event.
Por qué hooks y no una clase base o una interfaz. Porque el núcleo es procedural y no necesita un framework de plugins. Dos callables opcionales resuelven el caso sin acoplar el runner a FastAPI, a hilos ni a SSE. El runner sigue pudiendo ejecutarse desde la CLI exactamente igual, con on_epoch=None y should_stop=None.

6.4 Lo que la UI deliberadamente no hace

  • No reimplementa la validación. schemas.py valida forma; la metodología se consulta en space.
  • No recalcula métricas. Las recibe del runner (validation_metrics, matriz de confusión, F1 macro, etc.) y las presenta.
  • No reanaliza las suites. evidence.py agrega lo exportado; el informe inferencial lo produce analyze.
  • No inventa una taxonomía de fallos. La deriva de f1_macro y epochs_executed reales.
  • No escribe en el store de las suites. Usa results/ui-runs/, separado de results/experiments/ (ver §7).

El contraste de flujos queda así:

Antes: solo CLI

generate → run → compare → aggregate → export → analyze → HTML/PDF Un comando por etapa. Sin estado en vivo. La curva se ve al final.

Ahora: CLI + UI

POST /api/runs → job_id → SSE epoch/epoch/... → done (metadata) → store aislado La misma config, el mismo runner, el mismo formato. Solo cambia el transporte.

7. Persistencia y aislamiento de datos

La UI escribe en un store propio, por defecto results/ui-runs/ con experimento ui-exploratory. Se puede cambiar con PREBENCHMARK_UI_STORE y PREBENCHMARK_UI_EXPERIMENT. La razón es simple: un job interactivo no puede contaminar exp-sweep-*, que es la evidencia de las suites y la base de los informes.

results/ ├── ui-runs/ ← store de la UI (aislado) │ └── ui-exploratory/ │ ├── <run_id>/ │ │ ├── metadata.json configuración, dataset_version, entorno, estado, métricas │ │ └── epochs.csv historia train/val por época │ └── configs.jsonl registro append-only de configuraciones ├── experiments/ ← store de las suites (intacto) ├── exports/<experiment>/ ← master/configs/epochs/aggregates CSV └── reports/<experiment>/ ← analysis_<ts>.html y .pdf

La escritura la hace ResultsStore, no el servidor: el servidor solo le pasa la raíz. Eso hereda las garantías del núcleo —escritura atómica de metadata.json mediante temporal + os.replace, y configs.jsonl append-only deduplicado por config_id— sin reimplementar nada.

Consecuencia de --reload. Uvicorn con --reload levanta un proceso reloader y un proceso worker. Al cambiar un archivo, el worker se reinicia y los jobs en memoria (JobRegistry) se pierden. Lo ya persistido en results/ui-runs/ sobrevive. Para producción se corre sin --reload.

9. El frontend: dos pestañas y un EventSource

El cliente es deliberadamente simple y sin dependencias. El flujo de la pestaña de corrida es:

  1. Inicialización. init() pide /api/options y /api/health, llena los selectores con lo que publica el servidor y engancha los controles.
  2. Selección de dataset. loadDataset() consulta /api/datasets/{name}, muestra muestras/features/clases/desbalance y actualiza la arquitectura estimada.
  3. Validación en vivo. Cada cambio se debouncea y se manda a /api/validate. El resultado se pinta como advertencias o errores; una configuración INVALID bloquea el botón.
  4. Evidencia. loadEvidence() consulta /api/evidence?dataset=... y muestra las familias problemáticas del dataset, con su modo de fallo inferido.
  5. Corrida. startRun() hace POST /api/runs, guarda el job_id y abre openStream(jobId).
  6. Streaming. Los listeners de EventSource actualizan estado, agregan filas a curveRows, redibujan la curva y, al llegar done, renderizan métricas, matriz de confusión y el visor de metadata.json.
  7. Cancelación. cancelRun() hace POST /api/runs/{id}/cancel; el servidor responde de inmediato y el corte efectivo ocurre al final de la época en curso.
  8. Comparación local. Hasta tres corridas se guardan en el array runs y se muestran en una tabla con botón de remoción por fila. Es comparación de sesión, no de suite: para eso está la pestaña 2.

El servidor no mantiene el estado del formulario ni la tabla comparativa: eso vive en el navegador. El servidor solo conoce jobs y evidencia. Esa separación evita sesiones y simplifica el esqueleto; el costo es que al recargar la página se pierde la tabla comparativa local.

10. Decisiones, límites y tradeoffs

DecisiónPor quéCosto / límite asumido
Un solo worker de entrenamiento Los RNG son globales al proceso; dos corridas concurrentes romperían la reproducibilidad. Las corridas se serializan. El paralelismo real requiere procesos (§11).
Jobs en memoria Simplicidad para un esqueleto interactivo; no hace falta una cola durable. Un reinicio pierde los jobs en vuelo. Lo persistido en el store sobrevive.
SSE en vez de WebSocket El flujo es unidireccional (servidor → cliente) y SSE es nativo, con reconexión automática del navegador. No hay canal cliente → servidor por el stream; cancelar usa otro endpoint.
Lectura por cursor cada 50 ms El hilo de entrenamiento no puede await; un log append-only con índice es simple y seguro entre hilos. Latencia de hasta ~50 ms y costo mínimo de sondeo. Se envía ping cada 15 s.
Log de eventos con tope (2000) Evita crecimiento ilimitado de memoria en jobs largos. Pasado el tope se dejan de registrar épocas nuevas (el contador y el evento final siguen).
Store aislado results/ui-runs La UI no puede contaminar la evidencia de las suites. La comparación general no incluye automáticamente las corridas de la UI; hay que exportarlas si se quieren agregar.
Set de prueba reservado por defecto Evita fuga de información y mantiene el protocolo: se compara por validación, el test es para evaluación final. El cliente debe pedir include_test=true explícitamente y la respuesta lo marca.
Cancelación cooperativa por época Abortar a mitad de una época dejaría estado inconsistente. La cancelación no es instantánea: espera el final de la época en curso.
Sin autenticación ni CORS abierto Herramienta local de investigación, un solo usuario. No debe exponerse a una red no confiable tal como está.
Endpoints def (no async) para lo corto FastAPI los corre en su threadpool; no bloquean el loop aunque hagan I/O de archivos. Ocupan un hilo del pool mientras dura la operación (validar, leer CSV).
Límite que conviene tener presente. /api/runs y /api/validate llaman a dataset_base_config, que puede resolver y cachear un dataset. La primera vez que se usa un dataset con force_load, esa operación puede tardar (red incluida) y ocurre en el hilo del request, no en el worker. Para datasets ya cacheados es inmediata. Si se quisiera eliminar esa latencia, el paso siguiente sería precargar en el lifespan o mover la resolución a un job.

11. Camino al benchmark definitivo

El esqueleto ya demuestra el patrón completo: HTTP → validación de dominio → job → hilo → SSE → store. Lo que falta para un benchmark definitivo no es reescribir esto, sino escalarlo y endurecerlo. Ordenado por impacto:

  1. Paralelismo por procesos. Reemplazar el ThreadPoolExecutor de un worker por un pool de procesos (por ejemplo ProcessPoolExecutor o workers externos tipo Celery/ RQ). Cada proceso tiene su propio RNG global, así que la reproducibilidad se mantiene. El JobsRegistry pasaría a ser un coordinador, no un executor.
  2. Cola durable. Persistir el estado de los jobs (SQLite o similar) para sobrevivir reinicios y poder reanudar o auditar. Hoy el estado vive solo en memoria.
  3. Barridos desde la UI. Exponer generate_configs + run --multi-seed como un "suite job" que encola N corridas y muestra progreso agregado. El dominio ya lo soporta; falta la capa de orquestación.
  4. Comparación con evidencia de suite. Permitir que una corrida de UI se exporte y se agregue al análisis, para que la comparación general incluya también lo exploratorio.
  5. Pestaña de funciones de activación. Ya está anunciada y deshabilitada; requiere curvas comparativas por activación, que el export ya contiene.
  6. Autenticación y límites. Si se expone fuera de localhost: auth, CORS restringido, rate limiting y cuotas de CPU/memoria por job.
  7. Persistencia del stream. Si se quiere reconexión exacta tras un corte, honrar Last-Event-ID en lugar de replay desde cero (hoy el servidor siempre empieza en el índice 0, que es correcto para corridas cortas).
Lo que no hay que cambiar. La dirección de dependencia. El núcleo prebenchmark/ no debe importar server/. Los hooks on_epoch y should_stop son la frontera: cualquier transporte futuro (CLI, UI, API externa) los usa igual. Si esa dirección se invierte, se pierde la posibilidad de correr el mismo experimento desde la consola y desde la web con resultados comparables.

Correr los tests

python -m pytest -q

La suite corre offline con datasets en memoria. Los tests del servidor montan create_app con un store temporal, que es exactamente para lo que existe la fábrica.

Agregar un endpoint nuevo

  1. Si necesita un tipo de request/response nuevo, declaralo en schemas.py.
  2. Si toca dominio, llamá a prebenchmark; no reimplementes la regla en el servidor.
  3. Declará la ruta dentro de create_app, usando _service(request) para acceder al estado de larga vida.
  4. Si la respuesta puede traer objetos de NumPy, pasala por to_jsonable.
  5. Si es I/O corto, def; si necesita esperar sin bloquear, async def.

Cambiar el store o el experimento de la UI

$env:PREBENCHMARK_UI_EXPERIMENT = "ui-exploratory-2"
python -m uvicorn server.app:app --reload

13. Resumen en diez ideas

  1. El servidor es una fachada sobre prebenchmark; no un segundo sistema.
  2. El entrenamiento corre en un hilo dedicado, fuera del event loop, para que la página nunca se congele.
  3. El puente es el Job: estado compartido, protegido por lock, observable por SSE.
  4. Un solo worker porque los RNG son globales al proceso; es una decisión de reproducibilidad.
  5. POST /api/runs responde 202 al instante; el progreso llega por /events.
  6. Los dos hooks del runner —on_epoch y should_stop— son toda la extensión que el núcleo necesitó.
  7. La validación metodológica vive en space; Pydantic solo valida la forma.
  8. El set de prueba queda reservado salvo pedido explícito y marcado como tal.
  9. La UI escribe en results/ui-runs, aislada de la evidencia de las suites.
  10. La evidencia no se hardcodea: se deriva de las corridas reales, con umbrales relativos al dataset.
